# 应用形态决策

先选能真正满足运行边界的形态，再写代码。不要把每个需求都压缩成单文件 HTML 或云端模型调用。

| 条件 | 推荐形态 | 关键边界 |
| --- | --- | --- |
| 一次性操作 | Agent 直接执行 | 不创建应用。 |
| 重复使用、依赖 Proma Browser / MCP / Skills / 已连接账户 | Proma 内工作流 | 实际动作由 Agent 完成；网页不能继承这些权限。 |
| 本地填写、计算、浏览、筛选或生成，不需要后端 | 静态网页或单页 Web 工具 | 不创建 app key。 |
| 有复杂状态、多个页面或本地数据 | 轻量 Web 项目 | 选择最少依赖的框架或原生 Web。 |
| 需要离开 Proma 独立调用 AI | Web / CLI / 服务，并按需接入 Open API | 先完成动态模型发现与密钥边界设计。 |
| 多人、公开链接、共享数据、登录或长期持久化 | 前端 + 服务端 / 用户指定架构 | 密钥只在服务端；明确部署和身份策略。 |
| 用户指定技术栈或运行环境 | 用户指定架构 | 不以默认网页覆盖。 |

## 默认网页交付

没有架构约束时，优先做用户可立即预览和操作的网页。项目规模应匹配需求：

- 单一输入输出流程：单文件 HTML 可以是最小交付。
- 需要模块化、路由、状态管理或测试：建立正常项目结构，不因“默认网页”牺牲可维护性。
- 需要上线：先确认目标平台和公开范围；本地预览不等于部署。

网页需要具备真实核心交互、清晰的空状态/错误状态，以及移动端基本可用性。用 `BrowserPreviewOpen` 验证，不只依赖源码阅读。

## Proma 内工作流的表达

网页可作为工作流面板、说明页或结果视图，但不能直接调用只有 Agent 才具备的工具。交付中应区分：

- **网页本身完成的事**：纯本地 UI、数据转换或安全的后端 API 调用。
- **Proma Agent 完成的事**：浏览网页、访问本地文件、调用已安装 Skill/MCP、使用授权账户。
- **用户需要做的事**：提供输入、授权外部副作用、启动预览或部署。
