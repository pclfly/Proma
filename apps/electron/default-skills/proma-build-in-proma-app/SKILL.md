# Proma 内应用构建器

将“帮我做一个”从一次性代码输出，变成适合在 Proma 内持续使用、验证和迭代的产品化交付。先判断问题应该由 Proma 的现有能力解决，还是需要一个独立应用；再选最小而正确的形态。

## 先做判断

| 用户真实目标 | 优先做法 |
| --- | --- |
| 只是要完成一次任务 | 直接完成任务，不为它造应用。 |
| 需要利用已连接的工具、文件、浏览器、MCP、Skills 或 Agent 权限反复执行 | 将它设计为 **Proma 内工作流**；真实调用继续由 Agent 和对应工具完成，不假装普通网页能获得这些权限。 |
| 需要用户反复填写、查看、筛选、比较或生成结果 | 默认构建一个可预览的 **网页应用**。 |
| 成品必须在 Proma Agent 不在场时自行调用模型 | 在正确架构中接入 **Proma Open API**。 |
| 用户已经指定 Web 框架、CLI、桌面端、后端、部署方式或仓库约束 | 尊重指定架构，不用“单文件 HTML 默认”覆盖它。 |

Proma 的能力是优先选项，不是强行套用的理由：网页无法直接继承 Agent 的 Browser、MCP、Skills、Vault 或本地文件权限。遇到这类需求，要明确边界，并把运行步骤留在 Proma Agent 工作流中；若用户需要独立运行，再设计具备相应服务端与授权边界的架构。

## 默认交付：先做网页体验

用户没有指定架构时，优先创建一个适合任务的网页应用，而非默认生成含密钥的单文件 AI demo。

- 简单、纯本地逻辑：可用单文件 HTML。
- 有状态、数据、多个视图或可维护交互：创建结构清晰的轻量 Web 项目。
- 需要对外分享、多人使用或持久化：先说明需要的部署、身份和服务端边界；不要把密钥放进前端。
- 用户需要公开访问链接时，使用匹配的部署能力或 Skill；不要把“本地预览”表述为已发布。

构建时：

1. 把用户目标转为最小可用流程、输入、输出与验收标准；能从上下文推断的不要反问。
2. 使用可访问、响应式的界面，避免只交付没有真实交互的视觉稿。
3. 涉及界面细节时读取 `make-interfaces-feel-better`；视觉素材使用本地已有资产或用户提供的图片，不要调用外部生图服务。
4. 在授权工作区生成文件，并用 `BrowserPreviewOpen` 预览；用 `BrowserObserve` 核验结构，必要时用截图检查视觉结果。
5. 交付可运行路径、如何继续在 Proma 中迭代，以及尚未实现或需要外部服务的边界。

## Proma 能力接入策略

### Proma 内工作流

当功能依赖 Agent 的浏览器、文件、MCP、Skills、日程、邮件或其他已连接服务时：

- 优先用当前已存在的专用工具 / Skill 实现实际动作。
- 网页可以充当说明、输入收集、结果展示或本地工作台，但不能声称自己直接拥有 Agent 的权限。
- 清楚标注“由 Proma Agent 执行”的步骤，以及需要用户授权的外部副作用。
- 如流程会长期重复且适合无人值守，再按 `automation` Skill 判断是否创建自动任务；纯提醒不创建 Automation。

### Proma Open API

仅在成品要离开当前 Proma Agent 独立工作，且确实需要模型、图像、向量或兼容 API 时接入。读取 `references/open-api-integration.md`，必要时再读取 `proma-cloud-sdk` 的对应 reference。

- 不需要 Open API 的网页不要创建 app key。
- 为独立应用创建 `app-` 专用 key，绝不复用 Agent inner key。
- 本地私有原型可以把 key 写入应用，但必须明确“文件不可分享”；推荐将 key 放在 `.env`。
- 公开、多人或可部署的产品必须把 key 放在服务端环境变量，前端不得取得或打包该 key。
- 返回给用户 key 名、额度和 Proma 设置中的管理位置；不要在 README、日志、提交或 `.env.example` 泄露真实 key。

## 模型选择：实时发现，不预设推荐

本 Skill 不包含任何固定模型、模型家族、价格或“默认最佳模型”。只要成品要调用模型，Agent 必须：

1. 由用户提供可用的 Proma API Key 与 base URL，不要读取或复用 Agent 的内部凭据；将 base URL 归一化为根地址。
2. 拉取 `GET /v1/models`；需要协议、能力或价格元数据时再拉取 `GET /api/v1/models`。
3. 依据当前目录中的可用性、任务类型、上下文长度、所需输入/输出能力、协议与成本，选择模型和 API 表面。
4. 在最终应用中只写入这次实时选择的模型；若用户希望可切换，在构建时从实时目录生成允许选项，或由安全的服务端提供目录。
5. 根据返回元数据选择正确协议，不能假设所有模型都兼容同一种请求体。模型列表或调用失败时，如实说明并停止猜测模型 ID。

模型发现属于 Agent 的构建职责，不要求终端用户选择、复制模型名或手动维护静态推荐表。

## 标准执行顺序

1. **收敛目标**：判断一次性任务、Proma 内工作流、网页应用，还是独立产品；只询问会改变架构或安全边界的少量问题。
2. **选择架构**：默认网页优先；用户明确架构优先；涉及权限、多人或公开部署时先设计服务端边界。
3. **实现最小闭环**：让用户能完成核心任务，再补非核心功能。
4. **按需接入 Proma 能力**：只有独立 API 功能才创建 app key；模型一律先实时发现。
5. **验证和交付**：本地网页必须预览核验；给出启动/预览/部署方式、实际接入能力和安全边界。

## 不要这样做

- 不要把所有“做个工具”都降级为带 API key 的单文件聊天页。
- 不要把 Agent 专属能力伪装成浏览器前端能直接调用的 API。
- 不要为了接入模型而强行创建 key，也不要把 key 发送到公开端、客户端仓库或版本控制。
- 不要硬编码模型 ID、模型价格、协议假设或静态“推荐模型”。
- 不要因用户未指定技术栈就拒绝做 Web、服务端或复杂应用；先选择与需求匹配的最小架构。
- 不要只生成代码不预览、不验证，或把本地文件称为已部署产品。
