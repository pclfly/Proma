# 官方 0.22.0 → 0.22.80 增量同步方案

> 执行方式：方案经用户确认后，使用 `superpowers:executing-plans` 按批次实施并设置验收点。当前只交付方案，不启动实施，不自动提交；需要并行代理时另行确定。

**Goal:** 在保留 Proma-dev 本地定制、数据与权限边界的前提下，将官方 0.22.28、0.22.60、0.22.80 的适用功能和修复增量同步到现有源码。

**Architecture:** 采用“旧官方基线 → 新官方样本 → 当前源码”的三方行为对照，而不是覆盖官方 bundle 或按版本逐个全量合并。主进程服务、Pi utility runtime、共享契约、preload 与 renderer 必须一起闭环；Cloud 付费服务与平台专属功能单列，不伪造能力。大范围 UI 迁移按功能独立验收，不把已有本地增强退回官方旧行为。

**Tech Stack:** Bun monorepo、TypeScript、Electron、Pi Agent runtime、React、Jotai、Radix/shadcn、现有 Markdown/KaTeX/Shiki 工具链、JSON/JSONL 原子持久化。

## 2. 路线选择

1. **推荐：按能力分批增量适配。** 把官方新增行为落到现有源码，保留 fork 差异，每批可运行、可回退。成本高于直接覆盖，但最符合当前大量本地改动的实际状态。
2. **逐版本完整对齐。** 0.22.28 → 0.22.60 → 0.22.80 逐次复制架构；会反复修改 UI，例如先补岛上额度又立即删除岛，重复成本高，不推荐。
3. **只做运行时和 Bug 修复。** 风险较小，但不能交付连续改动、Skills 新中心、自操作等新能力，不符合“继续更新”的完整目标，仅适合作为第一阶段里程碑，不能悄悄缩减成最终范围。

## 3. 实施批次与依赖

顺序：**P0 基线 → P1 运行时/模型 → P2 稳定性/自动化 → P3 检出/改动/PR → P4 阅读/布局 → P5 Skills → P6 渠道/额度/岛退役 → P7 自操作 → P8 总验收**。

每批先写正常路径及主要边界的 BDD 回归，再实施，再最小测试及 typecheck；涉及依赖、进程、IPC 或打包规则时追加 Electron 构建。不能用仅检查源码字符串的测试替代真实行为测试。
